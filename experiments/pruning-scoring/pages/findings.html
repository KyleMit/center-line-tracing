A diagnosis nobody profiled, and the sweep it was blocking

The handoff's next task was to sweep skimage-skan's raster scale. It could not run until one leaderboard cell stopped hanging — and the recorded reason for that hang was wrong. Fixing what was actually slow made every measurement in this layer four times faster, unblocked three things marked "did not finish", and let the sweep run. The sweep then overturned the claim that motivated it.

Result

Handoff item 1.
10 drawings × 5 scales, each auto-pruned.

Run skimage-skan at raster scale 8, not 4

skimage-skan leads the cross-backend leaderboard but only ever published one raster scale. Sweeping it moves all three axes in the same direction at once — which is the whole reason to believe it.

Reconstruction error alone would not be enough. This layer's own smoothness work exists because error rewards a path that wiggles along the outline: a denser raster can buy accuracy by chasing the boundary, and the leaderboard cannot tell that apart from genuine improvement. So the sweep scores each scale on error and on the product goal — wobble, and control points per stroke width. If scale 8 were cheating, wobble would go the other way. It does not.

The gain is in the extraction, not in the selection rule. The same improvement is present in the unpruned column — median error at λ=0 goes 0.0188 at scale 4 to 0.0176 at scale 8 — so pruning is merely not throwing it away. That check matters, because the selector is free to trade error for simplicity and a scale that happened to suit its tolerance would look better for the wrong reason.

Scale 16 does not continue the trend

skimage-skan's own notes nominated scale 16 as the experiment to run. Over the nine drawings that completed all five scales, error is flat (0.0187 vs 0.0188), wobble is worse than scale 8 (0.0185 vs 0.0178), points per width is identical, and extraction is 5.8× slower again. The answer is no.

The exception worth routing on

sun-square and landscape-square want scale 2. sun-square is skimage-skan's worst cell in the entire leaderboard, and it is worst because of the scale, not the backend: it is thin tapering rays, and above scale 2 the taper tails resolve into skeleton structure that pruning then has to guess about. At scale 2 its error drops from 0.0390 to 0.0246 — a 37% cut from changing one number.

Negative result

Only ground truth could show this.

Pruning does not clean up after a finer raster

The reasoning that justified the whole sweep was skimage-skan's note: "scale 4 is the default here; scale 8 is the right choice if a pruning stage will clean up after it." This layer is that pruning stage, so the conditional is testable. It does not hold.

Reconstruction error cannot answer this — a spurious branch that hugs the outline barely moves it. The corpus can: skimage-skan's twenty synthetic cases were generated from known centerlines. Case 20 is the stress test, a single straight capsule under boundary jitter, whose correct answer is one branch at every scale.

There is a corroborating signal in the selection rule itself. On house-tall, dinosaur-wide and home-wide the selector picks λ = 0 at scale 8 — it declines to prune at all — where at scale 1 it picks 3.0, 1.0 and 0.0. So at high resolution the rule is not merely failing to remove enough; it is often deciding there is nothing worth removing. Whatever is wrong lives in the decision, not only in the threshold.

And ground truth tempers the recommendation too

Median distance to the true centerline over the twenty cases converges by scale 4 and then stops improving, while the P95 is best at scale 4. So the scale-8 win on real drawings is a reconstruction-and-smoothness win, not a "the line sits in a more correct place" win. Worth stating plainly, because the leaderboard cannot tell the difference and this is the first measurement in the track that can.

The measurement itself — clg.metrics.centerline_error — is new, and now sits in the shared layer rather than in one track. That is a partial down-payment on what the handoff calls the single most useful missing measurement. It was validated against skimage-skan's own implementation to sixteen digits, and covered by the invariant tests.

Correction

The recorded diagnosis had become the next session's task list.

It was never merge_chains

One leaderboard cell — polygon-voronoi/landscape-square — had never completed a pruning sweep. The handoff attributed it to an O(V²) re-queue scan in graph canonicalization, and prescribed the fix in detail.

On that graph, merge_chains runs in 0.0 seconds and performs zero merges. The cost was somewhere else entirely: in metrics.boundary_distances, where shapely.distance(points, one_big_boundary) is a linear scan over every boundary segment for every sample point. On a graph with 28,000 control points re-stroked against a dense source outline that is 30 s per call and 97 s for a single score — and a λ sweep scores every candidate.

Why this is the useful part

The wrong diagnosis was written down confidently enough to become a prescribed task — "a set-backed queue and an incremental degree map, the first thing to do if this layer is productionized" — and nobody had run a profiler. The O(V²) scan was real and is fixed too. It simply was not what was biting.

The original paragraph is kept verbatim in NOTES with a correction banner rather than rewritten, because a research log that quietly edits its wrong turns stops being evidence about how the work actually went.

Defect

Found by re-running something that should have been idempotent.

The leaderboard was scoring its own previous output

Every other backend's input graphs live in debug/<track>/graphs. The incumbent's lived in debug/pruning-scoring/graphs/incumbent/ — which is also where each cell promoted its winner. Same path.

So each run fed the previous run's pruned, canonicalized graph back in as "what the incumbent published". The drift always ran in the flattering direction, because canonicalization lets the radius profile interpolate across spliced chains instead of using a per-edge median, which makes the re-stroke fit better.

A second one in the same family

bench.py and abtest.py each write a report at the end of a run — and it is not the published report. Those come from lbreport.py and abreport.py, which say materially different things: abreport.py canonicalizes both sides before measuring complexity, without which flo-mat's hand-tuned graph appears seven times more complex than it is. Re-running a bench silently downgrades the committed document. I hit this myself; the reporter step is now marked mandatory in the handoff.

Unblocked

Both were "did not finish in the session" in the previous handoff.

The eightieth cell changes an argument

With scoring 13× faster, the cell that never completed simply runs — and polygon-voronoi wins landscape-square outright at 0.0159, ahead of every other backend.

polygon-voronoi has both the best single score in the table (0.0118 on sun-square) and a middling median. That was already the hybrid-routing argument — but it rested on one drawing. Now it rests on two, and best-backend-per-drawing lands at 0.0162 against skimage-skan's 0.0188: 14% better, where the previous measurement said 7%.

The A/B went from 18 cells to 30, and got a stronger claim

Adding landscape-square back and running polygon-voronoi as a third pair changes what the A/B can say. Against flo-mat's SAT threshold and tegaki's own rule, automatic pruning buys simplicity at roughly equal error — the existing conclusion. Against polygon-voronoi's PyGeoOps width-relative filtering, which is the only genuinely tuned opponent in the set, it wins on error, on all ten images.

Not done

One cell of fifty, and it is the expensive one

dinosaur-wide at scale 16 did not finish in 47 minutes, so the sweep is 49/50 and every scale-16 median above is over nine drawings rather than ten. Rasterizing per element at 16 px per unit puts medial_axis on masks large enough that cost stops tracking the median — which is a further practical argument against scale 16 rather than a gap in the argument for scale 8. The report distinguishes an absent cell from a failed one instead of printing a bare dash.

Two things this work does not establish, said plainly. Wobble is a property of the recovered path, not of how close it is to the line a person drew — the ten real drawings have no ground truth, so a path can be beautifully smooth and in the wrong place. And the corpus result is one backend against one track's corpus; the tracks still cannot be compared on truth until the corpora are unified.

What to do next
  1. Add a curve-fitting pass — the sweep shows error and smoothness moving together, so there is room.
  2. Unify the synthetic corpora. The measurement now exists; only the corpus is missing.
  3. Decide whether raster scale is routed per drawing. sun-square alone is −37%.
  4. Find out why pruning stops keeping up with resolution. λ is scale-free by construction, so this should not happen.
